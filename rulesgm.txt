Goal Model Design and Compilation Rules

These rules define a structurally valid KAOS Goal Model that can be translated into the restricted GR(1) fragment used by the current workflow.

1. Strict decomposition (the refinement tree)

Every model should begin with abstract root goals that describe the final purpose, for example Achieve [MissionCompleted].

Use AND refinements to decompose complex goals. A complex mission may require multiple Achieve leaves for its independent subtasks.

Stop decomposition only when a leaf is a Requirement fully controlled by robot outputs, a Domain Property describing immutable physical behavior, or a Domain Assumption describing behavior that the environment is expected to provide.

2. Strict variable ownership (the agent principle)

GR(1) synthesis is a two-player game with perfect information. Each atomic proposition must belong to exactly one agent.

The system must never define the next state of an environment variable. A system goal should constrain controller outputs, while an environment assumption should describe the corresponding physical response.

3. Strict temporal classification (leaf syntax)

The synthesis tool does not accept arbitrary full LTL. Leaf nodes must use these temporal categories:

- Initialization defines the state at step zero. It must not contain temporal operators or next-state references.
- Safety (Maintain or Avoid) defines valid transitions. Use the next-state operator (') to connect the current state to the immediate future when a transition is required.
- `Goal Maintain` leaves must use `G(p -> G q)`. The compiler creates an input latch monitor `m` with `!m` initialization, transitions `G((m' -> (m | p)) & ((m | p) -> m'))` and `G((m | p) -> q)`. The generated constraints belong to the environment when `q` is an input and to the system otherwise. The monitor is always an input.
- `Goal Achieve` leaves must use `G(p -> F q)`. The compiler creates an input pending monitor `m`, initializes it with `!m`, defines `pending = (m | (p & !q)) & !q`, adds `G((m' -> pending) & (pending -> m'))`, and adds the liveness condition `!m`. The monitor transition belongs to the environment because `m` is an input; the generated obligation belongs to the environment when `q` is an input and to the system otherwise. The monitor is always an input.
- Liveness defines something that must happen repeatedly. The compiler also retains direct `GF B` support for existing models:
	- `GF B` is unconditional liveness: B must recur according to the GR(1) liveness semantics, whether or not another event occurs. It is written directly in `[ENV_LIVENESS]` or `[SYS_LIVENESS]`.
	- `G(A -> F B)` is conditional response liveness: whenever trigger A occurs, B must eventually follow. It does not require B when A never occurs, so it is not equivalent to `GF B`. The compiler encodes this form with a monitor transition in `[ENV_TRANS]` or `[SYS_TRANS]` and a monitor obligation in the corresponding liveness section.
- Do not nest complex temporal operators such as `F(G(x))`.

4. Liveness pairing (starvation prevention)

For every system Goal Achieve that depends on an external condition, provide a corresponding Assumption [Name] whose FormalDef is a liveness formula.

If the system has a liveness goal requiring a system action, but a safety rule permits that action only when an environment condition is true, the environment needs an Assumption guaranteeing that condition after the relevant trigger. Without this pairing, the environment can win by doing nothing.

5. Physical completeness of the environment (inertia and mutex)

Synthesis treats the environment as chaotic and adversarial unless the model constrains it. Add inertia assumptions for every environment variable representing the physical world. The environment must not teleport an entity between incompatible states. If the system does not issue a transition command, a state sensor should retain its value in the next state, for example `(p & !u) -> p'`. Add mutex assumptions where physical states cannot coexist, such as `!(p & q)`.

6. Domain properties and domain assumptions

- `DomainProperty [Name]` describes immutable physical behavior, such as a mutual-exclusion constraint. It is compiled as an environment transition constraint and must not be changed, criticized, or proposed for revision by the LLM checker.
- `Assumption [Name]` describes environment behavior that may fail, such as an external event occurring or a device responding. It is compiled like an `Assumption` and may be criticized, suggested, or revised by the LLM checker.
- Domain properties must not be used to guarantee a system output. Domain assumptions may constrain or guarantee only environment inputs.

7. Explicit player ownership by header

The header determines which player owns the proposition and which GR(1) section receives its FormalDef:

- Initialization [EnvironmentName] assigns initial values to environment variables. These variables become SLUGS INPUTs.
- Initialization [SystemName] assigns initial values to system variables. These variables become SLUGS OUTPUTs.
- Assumption [Name] belongs to the environment. It's safety FormalDef becomes an environment transition constraint in [ENV_TRANS].
- Assumption [Name] with `F B` belongs to the environment and places B directly in [ENV_LIVENESS].
- Assumption [Name] with `A -> F B` belongs to the environment and places a generated response monitor in [ENV_TRANS] plus the monitor obligation in [ENV_LIVENESS]. Keep the standard `Assumption [Name]` header used by this Goal Model schema.
- Goal Maintain [Name] and Goal Achieve [Name] are classified by the ownership of their consequent `q`, not by the header. Their generated monitor is always an input. A consequent input is compiled into environment sections; a consequent output is compiled into system sections.

Therefore, domain properties are immutable environment facts, assumptions are revisable environment expectations, and temporal Goal leaves are classified by `q`. A physical response should be modeled as an Assumption with `G(p -> F q)`. A controller command should use a system-owned consequent. Every atom still needs exactly one matching Initialization declaration unless it is a generated monitor, which is always an INPUT.

Compiler contract from compile_to_gr1.py

- The canonical headers are Initialization [Name], Assumption [Name], DomainProperty [Name], Goal [Name], Goal Maintain [Name], and Goal Achieve [Name].
- Only lines beginning with FormalDef: are compiled. InformalDef and other explanatory text are ignored by the compiler.
- Initialization formulas define ownership. Variables initialized under an Environment header become INPUTs; variables initialized under a System header become OUTPUTs. Every later atom must have exactly one initialization owner.
- Predicate(a, b) is flattened to Predicate_a_b. && and || are normalized to & and |. Boolean atoms use identifiers. The supported operators and forms are !, &, |, ->, ', F, G, True, and False.
- Initialization leaves are state formulas only. Safety formulas may be invariants or implications; implications are preserved as `antecedent -> consequent`. An outer G(...) wrapper is accepted for safety formulas.
- Liveness is limited to GF B or G(A -> F B). G(A -> F B) is compiled with an internal response monitor. A and B must use already-owned variables and must not contain arbitrary temporal nesting.
- Domain properties and assumptions control environment INPUT transitions and liveness. Temporal goals are routed according to the owner of `q`; never assign one atom to both players.
- For direct liveness, the generated structured SLUGS model contains B in the relevant liveness section. For response liveness, it contains the monitor transition and `!monitor` liveness obligation; this is the expected encoding, not a system transition.
- The generated structured SLUGS model and parser output are the executable authority. Proposed formulas must compile without undefined variables, unsupported temporal nesting, or ownership conflicts.
- Candidate changes must match the existing Goal Model vocabulary, preserve the current workflow, and be small enough to review. If a new variable is necessary, specify its owner, initialization value, and model location.
